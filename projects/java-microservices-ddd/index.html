THE PRODUCT

Boundaries you
can follow.

The sample separates Customer, Product, Identity, and Order contexts into framework-free application layers and Spring Boot API hosts. A shared DDD kernel contains common primitives, while Order demonstrates cross-context calls through ports and HTTP adapters. It is a working MVP prototype, with in-memory persistence documented as an intentional limitation.

01 — DOMAIN MODELOwn the business rules

Keep entities, aggregates, and use cases separate from Spring-host concerns.

02 — INTEGRATIONCollaborate through ports

Order validates and prices a request by calling Customer and Product services.

03 — RESILIENCEBound upstream calls

Documented timeouts distinguish unavailable services from invalid requests.

WALKTHROUGH

Follow an order
across contexts.

The order flow is a concrete way to see the architecture at work: identity, ownership, application logic, and service-to-service boundaries each have a role.

Resolve the caller’s identity

Identity issues a token, and the Order API resolves the caller through the Identity service before acting on an order request.

Compose behavior across services

Order uses ports to validate the customer and products, calculates the total server-side, and returns an order with catalog details.

Keep ownership and failures explicit

Order reads are scoped to the caller. Upstream timeouts and failures are mapped to bounded HTTP responses rather than hanging indefinitely.
